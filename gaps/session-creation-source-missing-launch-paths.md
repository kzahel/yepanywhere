# Native copy result loss still requires explicit reconciliation

The November 1 six-path creation-source audit is repaired by the common
[admission owner](../topics/session-identity.md#creation-consolidation--november-3).
Queue saves original enqueue source across restart/edit/retry; review and
maintenance save their actual request source; native/peer creates keep explicit
API source independently of trusted receipts; fork-summary's final target and
restart-fork failures retain their original request source on permanent public
P before native copy. Archived generators have explicit internal reasons.
Existing-session messages do not relabel source and legacy unknown rows stay
unknown. [Plan 171](../docs/tactical/171-durable-session-identity-and-creation.md#final-consolidation-slice--november-3)
records the final caller inventory and evidence. The original audit remains in
git history; its absence-of-source defects no longer describe current callers.

One narrower crash boundary remains: a provider/file copy may succeed and the
owner may die before the exact native result N is committed beside P. SQLite
and native files/RPC do not share a transaction. P already retains original
source and copy intent, and its unresolved allocation claim quarantines unknown
native discovery in that namespace. The operation becomes uncertain and must
not automatically repeat the copy. A later native orphan cannot be labelled as
that operation using a matching title, parent, time or provider-origin guess.

Safe automatic recovery would need authoritative provider/owned-runtime result
correlation durable across that loss window. It is not established by successful
fork, continuation or metadata tests. Keep explicit evidence-based reconciliation
and the broad receipts capability unadvertised until that work is qualified.
This is separate from deleting duplicate creation engines, which is complete.
